## 批量下载限流修复（2026-10-11）

- 用户补充受影响版本为 2.0，未提供原器件列表、格式或错误文字。对照 `v2.0.0` 标签与修复前工作区，两版资源请求都没有正确处理 HTTP 429 和 `Retry-After`，没有发现固定 29 个器件的输入、队列或导出上限。
- 使用标签中的原始下载代码和相同的 urllib3 2.7.0，连接数字回环地址上的本地 HTTP 服务：每成功读取 29 个器件资料，服务返回一秒 HTTP 429 窗口。29 个全部成功；30、31、60 个批次出现失败，30 个批次的 C30 报“网络请求失败：too many 429 error responses”。这是可重复的限流故障注入，不代表已确认用户现场响应或官方固定配额。
- 原因：带 `Retry-After` 的 429/503 被 `Retry(status=0)` 提前转为异常，外层仅等约 0.7 秒便重试；没有该响应头的 429 则直接判为失败。同站点其他查询、预览和下载继续发出请求。
- 修复后由应用统一处理限流，解析秒数和 HTTP 日期；缺失、零值、过期或无效等待时间使用 5/10/20/40 秒递增间隔，最多四次重试。同一来源共享等待时间，其他来源可继续工作；等待前释放连接，停止可立即打断。超过两分钟的服务端等待要求明确报错并保持该来源的等待期限，不提前重试。
- 新增 `test_resource_network.py` 的 **12 项测试**：29/30/31/60 个器件、连续两个限流窗口、三路并发、STEP/OBJ/SchLib/PcbLib 文件与回调完整性、响应头处理、共享等待、单连接池释放、取消与文件保留、重试上限、长时间等待拒绝，以及普通 4xx/5xx 和缺失模型语义。修复前关键断言失败，修复后全部通过。
- `app/build.ps1` 本次运行 **468 项全量测试**，全部通过，包含日志故障诊断、代理、库转换与原有界面回归。
- 匿名公开网络使用固定 33 个真实器件，修复前后当前代码均为 32 个四格式成功、C49118400 因无官方 3D 关联而仅导出两类 AD 库；没有出现数量导致的失败。2.0 原始代码同样成功处理第 30–33 个器件，但 C23922 另有 `NONE` 颜色转换错误，该兼容问题已在现有 2.2.2 中修复。
